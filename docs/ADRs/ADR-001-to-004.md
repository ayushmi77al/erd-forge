# ADR-001: Diagram Engine — React Flow v12

**Status:** Accepted  
**Date:** 2026-09-10  
**Deciders:** Architecture Team

## Context

We need a diagram rendering engine for visualizing entity-relationship diagrams with 1,000+ nodes. The engine must support:
- Custom node rendering (table with columns, domain badges, PII indicators)
- Custom edge rendering (cardinality labels, colored connections)
- Drag-and-drop repositioning with position persistence
- Pan, zoom, minimap
- Programmatic viewport control (focus on entity, fit view)
- Virtualization/culling for large schemas

## Options Considered

| Option | Pro | Con |
|--------|-----|-----|
| **React Flow v12** | React-native, excellent custom nodes, active development, TS-first | Some performance limits at extreme scale (5,000+ nodes) |
| **Cytoscape.js** | Battle-tested at scale, graph algorithms built-in | Not React-native, custom DOM rendering |
| **JointJS** | Feature-rich | Large bundle, commercial license concerns |
| **D3.js** | Maximum flexibility | Too low-level; must build everything |
| **Konva.js** | Canvas-based, fast | Not DOM-based, accessibility harder |

## Decision

**React Flow v12** is the primary diagram engine.

**Cytoscape.js** will be used as the fallback for schemas exceeding 800 nodes (activated via `DiagramService.switchToLargeSchemaMode()`).

## Consequences

- Canvas nodes are standard React components — full styling and event handling available
- React Flow's internal state is NOT the source of truth; all positions must sync back to `projectStore` via `onNodesChange`
- `React.memo` is mandatory on all node components to prevent mass re-renders
- LOD (level-of-detail) must be implemented manually by reading `useStore(s => s.transform[2])` (zoom value)

# ADR-002: Storage — wa-sqlite (OPFS) + JSON Project Files

**Status:** Accepted  
**Date:** 2026-09-10  
**Deciders:** Architecture Team

## Context

We need local-only storage that:
- Requires no installation (no local server, no Electron required for v1)
- Supports SQL queries for the catalog (FTS, joins, aggregates)
- Produces human-readable, portable project files
- Works in a modern browser (Chrome 110+) without extensions

## Options Considered

| Option | SQL Queries | Human-readable | No install | Capacity |
|--------|-------------|----------------|------------|----------|
| **wa-sqlite (OPFS)** | ✅ Full SQL | ❌ Binary | ✅ | ✅ GB+ |
| **IndexedDB** | ❌ | ❌ | ✅ | ✅ |
| **localStorage** | ❌ | ❌ | ✅ | ❌ 5-10MB |
| **File System Access API (JSON)** | ❌ | ✅ | ✅ | ✅ |
| **SQLite WASM (official)** | ✅ | ❌ | ✅ | ✅ |

## Decision

**Dual storage approach**:
1. **wa-sqlite via OPFS** for the SQLite catalog database (fast queries, FTS5)
2. **File System Access API** for the `.erdforge` JSON project file (portability, human-readable)

The JSON project file is the **source of truth**. SQLite is a read-optimized projection.

**Fallback**: IndexedDB when OPFS is unavailable (Firefox < 111, iOS Safari)

## Consequences

- All project data must serialize to/from the JSON schema defined in `DATABASE_SCHEMA.md`
- SQLite migrations must be versioned (`storage/migrations/`)
- OPFS requires a cross-origin isolated context: `COOP: same-origin` and `COEP: require-corp` headers must be set
- The service worker must handle these headers for PWA mode

# ADR-003: SDL Parser — PEG.js Custom Grammar

**Status:** Accepted  
**Date:** 2026-09-10  
**Deciders:** Architecture Team

## Context

We need a parser for the ERD Forge Schema Definition Language (SDL). The parser must:
- Produce a typed AST for rendering and validation
- Provide precise error positions (line + column) for editor highlighting
- Run in a Web Worker off the main thread
- Parse a 1,000-table schema in < 500ms

## Options Considered

| Option | Pro | Con |
|--------|-----|-----|
| **PEG.js custom grammar** | Full control, precise errors, typed AST | Grammar maintenance cost |
| **Adapt DBML parser** | Partial compatibility | Limited extensibility, adds domain/metadata features we need |
| **Handwritten recursive descent** | No dependencies | High implementation cost |
| **ANTLR4 (TS target)** | Industry standard | Large runtime, complex build |
| **Nearley** | Flexible | Ambiguous grammar handling less predictable |

## Decision

**PEG.js 0.10.x** with a custom grammar (`src/parsers/sdl/grammar.pegjs`).

The grammar file is compiled at build time to a JavaScript module. The compiled parser is checked into source control as a build artifact to avoid a runtime compilation step.

## Consequences

- Grammar changes require a rebuild: `pnpm build:grammar`
- Grammar tests are written as plain text SDL snippets in `tests/unit/parsers/`
- Parser runs entirely in `workers/parser.worker.ts` — never on the main thread
- The SDL serializer (`SDLSerializer.ts`) converts the AST back to SDL text for code generation

# ADR-004: State Management — Zustand + Immer + Command Pattern

**Status:** Accepted  
**Date:** 2026-09-10  
**Deciders:** Architecture Team

## Context

We need state management that:
- Supports unlimited undo/redo (every schema mutation is reversible)
- Avoids mass re-renders on a canvas with 1,000+ nodes
- Is TypeScript-first with minimal boilerplate
- Integrates cleanly with React hooks

## Options Considered

| Option | Undo/Redo | TypeScript | Bundle | Learning Curve |
|--------|-----------|------------|--------|----------------|
| **Zustand + Immer + Command Pattern** | ✅ Custom | ✅ Excellent | ✅ Small | ✅ Low |
| **Redux Toolkit** | ⚠️ Complex | ✅ | ⚠️ Large | ❌ High |
| **MobX** | ⚠️ | ⚠️ | ⚠️ | ⚠️ Medium |
| **Jotai + custom history** | ✅ | ✅ | ✅ | ✅ Low |
| **XState** | ✅ | ✅ | ⚠️ | ❌ High |

## Decision

**Zustand 4 + Immer** for reactive state, with a **custom Command Manager** for undo/redo.

Architecture:
- `CommandManager` holds a history stack of `Command` objects
- Each `Command` implements `execute()` and `undo()` which produce the next/previous `ProjectState`
- Zustand stores are the UI view of the current project state
- Commands are the only permitted mutation path

## Consequences

- All schema mutations must be expressed as `Command` classes in `core/commands/`
- Direct `store.setState()` calls are forbidden for schema data (only for UI state like panel visibility)
- The `historyStore.ts` exposes `canUndo`, `canRedo`, `undoDescription`, `redoDescription` for UI
- Zustand devtools are enabled in development for state inspection
