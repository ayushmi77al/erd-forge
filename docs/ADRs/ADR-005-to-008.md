# ADR-005: Layout Engine — Eclipse Layout Kernel (ELK) in Web Worker

**Status:** Accepted  
**Date:** 2026-10-22  
**Deciders:** Architecture Team  
**Supersedes:** Main-thread Dagre layout (`@dagrejs/dagre`)  

## Context
ERD Forge's current auto-layout uses `@dagrejs/dagre` v3.1.1. Empirical baselines show that laying out 500 tables freezes the main UI thread for ~700 ms, causing severe frame drops. Furthermore, Dagre:
- Cannot run off-thread in a Web Worker cleanly.
- Lacks compound node hierarchy for grouping tables visually into domains or schemas.
- Uses `table.name` as node IDs, which collides when multiple schemas contain tables with identical names.
- Routes orthogonal edges poorly on dense relational graphs.

## Options Considered

| Option | Off-Thread Worker | Compound Groups | Bundle Cost | Ecosystem Stability |
|:---|:---:|:---:|:---:|:---:|
| **ELK (`elkjs` v0.12.0 via `elk-api`)** | ✅ Native worker factory | ✅ First-class compound hierarchy | ~1.2 MB worker bundle | ✅ Eclipse foundation standard |
| **Dagre (Web Worker wrapper)** | ⚠️ Complex serialization | ❌ No compound support | Small (~50 KB) | ❌ Unmaintained library |
| **D3-Hierarchy / D3-Force** | ⚠️ Custom implementation | ⚠️ Force simulation slow at 500+ nodes | Small (~70 KB) | ✅ Mature, but wrong paradigm for relational DAGs |
| **WebCola** | ⚠️ Constraint solver | ⚠️ Partial compound support | Medium (~200 KB) | ⚠️ Infrequent maintenance |

## Decision
Adopt **`elkjs` (pinned to `^0.12.0`)** via `elkjs/lib/elk-api` instantiated inside a Web Worker.

Key architectural rules:
1. **Off-Thread Execution:** Layout runs in `apps/web/src/core/layout/elkInstance.ts` via `new Worker(new URL('elkjs/lib/elk-worker.min.js', import.meta.url), { type: 'module' })`. `elk.bundled.js` is strictly prohibited.
2. **Compound Hierarchy:** Model domain/schema sheets as parent `ElkNode` structures containing child table nodes with dedicated group padding.
3. **Collision-Safe Identifiers:** Every table node is identified by qualified key `${schema || 'public'}.${tableName}`.
4. **Deterministic Grid Fallback:** Disconnected tables without foreign key relationships are arranged in a clean multi-column grid offset below the connected graph, rather than stacking at `{ x: 80, y: 80 }`.
5. **Race Condition Protection:** Every layout request carries an incrementing `layoutEpoch` and `AbortController` signal to discard late-arriving results.

## Consequences
- `calculateAutoLayout` changes its return type from synchronous `LayoutMap` to asynchronous `Promise<LayoutMap>`.
- Callers in `ERDCanvas.tsx` must trigger auto-layout only after `@xyflow/react`'s `useNodesInitialized` hook returns `true`.
- Main-thread UI responsiveness remains at 60 FPS even during 500+ table auto-arrangements.

# ADR-006: SQL Lineage Parser — WASM Adapter (@guanmingchiu/sqlparser-ts)

**Status:** Accepted  
**Date:** 2026-10-22  
**Deciders:** Architecture Team  
**Supersedes:** `node-sql-parser` (retained temporarily as fallback)  

## Context
`node-sql-parser` (v5.3.5) bundles 2.6 MB of uncompressed AST code into both the main web bundle and the lineage worker. More critically, it lacks modern data warehouse syntax support:
- Databricks syntax is approximated as Hive.
- Oracle queries fall back to Transact-SQL.
- Analytical clauses (`QUALIFY`, `PIVOT`, `UNPIVOT`, Snowflake `MATCH_RECOGNIZE`, BigQuery procedural blocks) fail to parse or corrupt the lineage graph.

## Options Considered

| Option | Native Dialects | WASM Speed | Type Safety | Bundle Impact | Maintenance |
|:---|:---:|:---:|:---:|:---:|:---:|
| **`@guanmingchiu/sqlparser-ts` (v0.63.0)** | **16+ first-class** | ✅ Near-native Rust WASM | ✅ Auto-generated TS types | ~600 KB gzipped | ✅ Apache DataFusion upstream |
| **`node-sql-parser` (current)** | ~8 dialects with fallbacks | ❌ Pure JS regex/parser | ⚠️ Loose `any` AST types | 2.6 MB raw JS | ⚠️ Infrequent release cycle |
| **Peggy Custom SQL Grammar** | Tailored to ERD Forge | N/A | High | High authoring effort | ❌ Prohibitive grammar maintenance cost |
| **ANTLR4 Web Target** | Comprehensive | ❌ Slow JS runtime | High | >5 MB runtimes | ⚠️ Complex build tooling |

## Decision
Adopt **`@guanmingchiu/sqlparser-ts` (pinned to `^0.63.0`, Apache-2.0)** behind a new adapter interface (`SqlParserAdapter`).

Key architectural rules:
1. **Adapter Isolation:** Core lineage logic interacts exclusively with `NormalizedStatement`, isolating ASTWalker and SymbolTable from vendor AST shapes.
2. **Explicit Dialect Mapping:** Replace loose string casts with a validated `mapToWasmDialect()` function.
3. **Shadow Parity Gate:** `node-sql-parser` remains as an automated fallback. Cutover occurs on a per-dialect basis only after the candidate parser matches or exceeds lineage extraction accuracy on the checked-in fixture corpus.
4. **Worker Boundary:** Parsing and normalization execute inside `apps/web/src/workers/lineage.worker.ts`, keeping the main thread free.

## Consequences
- Lineage extraction becomes dialect-accurate for BigQuery, Snowflake, Databricks, PostgreSQL, MySQL, DuckDB, and ClickHouse.
- Upstream `sqlparser-rs` is a syntax parser, so AST normalization into `NormalizedStatement` is the primary engineering deliverable.
- Vite requires `optimizeDeps.exclude: ['@guanmingchiu/sqlparser-ts']` to prevent pre-bundling issues.

# ADR-007: Storage Layer — Official SQLite WASM with OPFS SAHPool

**Status:** Accepted  
**Date:** 2026-10-22  
**Deciders:** Architecture Team  
**Supersedes:** ADR-002 (`wa-sqlite` on IndexedDB)  

## Context
ADR-002 adopted `wa-sqlite` using internal example code (`IDBBatchAtomicVFS.js`). This operates on IndexedDB rather than genuine file system persistence, requires brittle `@ts-ignore` hacks, and still enforces COOP/COEP isolation headers.

The official `@sqlite.org/sqlite-wasm` module now offers consortium-backed WebAssembly with multiple Virtual File System (VFS) strategies.

## Options Considered

| VFS Strategy | Persistence | COOP/COEP Headers Required | Concurrency Model | Durability Risk |
|:---|:---|:---:|:---|:---:|
| **`opfs-sahpool` (Selected)** | **True OPFS File System** | **No (Headerless)** | **Single-tab exclusive** | **Zero (Native Disk)** |
| `opfs` / `OpfsDb` | True OPFS File System | Yes (`require-corp`) | Multi-tab safe | Zero |
| `IndexedDBAdapter` (Fallback) | IndexedDB Key-Value | No | Multi-tab safe | Low |
| `oo1.DB` (In-Memory) | Volatile RAM only | No | Single-tab | **Critical (Data wiped on reload)** |

## Decision
Adopt **`@sqlite.org/sqlite-wasm` (pinned to `^3.54.1-build1`, Apache-2.0)** using the **`opfs-sahpool`** VFS inside a dedicated Web Worker.

Key architectural rules:
1. **Worker Boundary:** Synchronous `db.exec()` runs inside `apps/web/src/workers/sqlite.worker.ts`. The UI communicates with the worker asynchronously via Comlink.
2. **Zero Silent Data Loss:** If `installOpfsSAHPoolVfs` fails (e.g. unsupported browser, private browsing mode), the engine falls back to the durable [`IndexedDBAdapter`](file:///c:/Users/ayush.mittal/Projects/erd-forge/apps/web/src/storage/IndexedDBAdapter.ts). Fallback to in-memory SQLite is strictly prohibited for catalog data.
3. **Single-Tab Coordination:** Coordinate tab ownership using `new BroadcastChannel('erd-forge-storage-lock')`. If a secondary tab opens, display a user-facing conflict modal offering to transfer active ownership.
4. **Idempotent Migration:** Legacy data is migrated to the SAHPool database in a verified transaction (`_migration_journal`). The legacy IndexedDB store is preserved as an untouched rollback source.

## Consequences
- OPFS persistence functions across standard web hosts without rigid server security headers (`Cross-Origin-Opener-Policy` / `Cross-Origin-Embedder-Policy`).
- Multi-tab access requires clear user-facing lease management.
- SQL queries and schema migrations gain official SQLite consortium maintenance and performance.

# ADR-008: Export Pipeline — Browser Canvas Hardening & OWASP CSV Sanitization

**Status:** Accepted  
**Date:** 2026-10-22  
**Deciders:** Architecture Team  

## Context
The canvas export utility (`exportUtils.ts`) suffers from three concrete vulnerabilities:
1. When exporting SVG or PNG, text reverts to Times New Roman if the client environment lacks local font files.
2. Base64 font embedding using `String.fromCharCode(...new Uint8Array(buffer))` throws `RangeError: Maximum call stack size exceeded` when font file sizes exceed call stack argument limits.
3. Exported CSV lineage data directly concatenates column values without sanitizing formula trigger characters (`=`, `+`, `-`, `@`), exposing spreadsheet users to formula injection.

## Decision
Retain **`html-to-image` v1.11.13** for DOM-aware `<foreignObject>` capture, enhanced with security and rendering hardening.

Key architectural rules:
1. **Chunked Base64 Conversion:** Convert font buffers using a 32KB chunking loop (`arrayBufferToBase64`), eliminating stack overflow risks regardless of font size.
2. **Font Embedding Scope:** Pre-load and inject `Inter Variable` font CSS scoped to `.react-flow__node`. Resolve font URLs dynamically relative to Vite's `base` path (`/tools/erd-forge/app/`).
3. **Explicit Vector Export Scope:** SVG export is explicitly scoped for **browser rendering, web embeds, and vector printing**. Direct importing of `<foreignObject>` SVGs into native desktop vector editors (e.g. Figma, Illustrator) is documented as out-of-scope (requires rasterization or dedicated SVG flattening).
4. **OWASP Formula Sanitization:** All CSV cells starting with formula triggers (`=`, `+`, `-`, `@`, `\t`, `\r`) are automatically neutralized by prepending a single quote (`'`).

## Consequences
- Canvas exports render with consistent Inter typography across all target environments.
- CSV lineage downloads are protected against spreadsheet code execution vulnerabilities.
- Export pipeline remains lightweight without requiring heavy server-side headless browsers.
