## 1. Executive Summary

Task T3.3 implements the multi-tab coordination lock for ERD Forge, safeguarding the local SQLite catalog (`opfs-sahpool`) and IndexedDB fallback against concurrent write collisions and database corruption across multiple browser tabs.

Because modern browser storage engines like OPFS `SyncAccessHandle` and atomic SQLite WAL journaling require single-writer semantics, opening ERD Forge across multiple tabs simultaneously risks lock contention or silent file locking exceptions. Task T3.3 introduces `TabLockCoordinator`, utilizing `BroadcastChannel('erd-forge-storage-lock')` with active leader heartbeats, a watchdog timer for automatic orphan recovery, and a non-destructive user modal (`TabConflictModal`) offering seamless session takeover or safe read-only browsing.

## 2. Architecture & Implementation

### 2.1 TabLockCoordinator State Machine (`storage/TabLockCoordinator.ts`)
- **Protocol:** BroadcastChannel `erd-forge-storage-lock` passing strongly typed messages:
  - `WHO_IS_LEADER`: Inquires if another tab holds an active lease.
  - `LEADER_HEARTBEAT`: Broadcast by the leader every 2,000 ms (or configured interval).
  - `REQUEST_TAKEOVER`: Transmitted by a follower tab requesting the leader to surrender write access.
  - `LEASE_GRANTED`: Emitted by the surrendering leader, granting leadership to the requester.
  - `RELEASE_LEASE`: Emitted on voluntary unload or release, signaling followers to claim the orphaned lease.
- **Roles:**
  - `leader`: Holds exclusive storage write lock and broadcasts heartbeats.
  - `follower`: Secondary tab observing leader heartbeats; writes are blocked.
  - `readonly`: Explicit read-only mode chosen by the user.
  - `unlocked`: Initialized state prior to lease election.
- **Split-Brain & Failure Resolution:**
  - If two tabs claim leadership simultaneously, deterministic tie-breaking by lexical `tabId` demotes the higher ID to follower.
  - A 5,000 ms watchdog timer monitors leader heartbeats. If the primary tab crashes, hangs, or closes abruptly without emitting `RELEASE_LEASE`, the watchdog detects the expired lease and promotes a follower tab to leader.

### 2.2 Storage Engine Write Guard (`storage/index.ts`)
- `StorageService` connects directly to `TabLockCoordinator`.
- `execute()` and `executeBatch()` strictly enforce that the tab is the active leader.
- If a secondary tab attempts a write while in `follower` or `readonly` mode, `StorageService` throws a descriptive exception (`Write rejected: Tab role is '...'`), preventing silent write races and catalog corruption.
- Read queries (`query()`) remain fully functional across all tabs.

### 2.3 User Experience & UI Modals (`TabConflictModal.tsx` & `App.tsx`)
- **TabConflictModal:**
  - Automatically displayed when a new tab opens and detects an active leader tab.
  - Displays the active leader's tab identifier and explains the Zero Silent Data Loss policy.
  - **Option 1 ("Take Over Session"):** Transmits `REQUEST_TAKEOVER`. The active tab steps down, and this tab becomes the primary writer.
  - **Option 2 ("Read-Only Mode"):** Allows inspecting diagrams and schemas without persisting changes to disk.
- **Session Revoked Alert Banner:**
  - If the primary tab yields leadership to another tab, a prominent warning banner informs the user: *"Session Inactive: Another browser tab took over database edit rights. This tab is operating in read-only follower mode."*
  - Provides a single-click "Reclaim Session" action.
- **Status Bar Integration (`StatusBar.tsx`):**
  - Displays live tab role badges: 🔒 `Primary`, 👥 `Follower`, or 👁️ `Read-Only`.
